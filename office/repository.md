# GitHub, дисциплины и утверждённый продукт

Действует с 09.09.2026 по прямому поручению Алексея; заменяет прежнее ограничение «только локально» для этого репозитория.

- Репозиторий: https://github.com/vetus-nauta/smeta, основная ветка `main`.
- Локальная рабочая копия: `/home/alexey/Groot/smetchik`.
- GitHub хранит согласованную историю правил, дисциплин, базы знаний, шаблонов и навыков. Незакоммиченная локальная правка ещё не является опубликованной версией.
- Репозиторий публичный. Размещаем только материалы отдела и разрешённые к такому размещению продукты; секреты, лицензии и постороннюю личную память не переносим. Если конкретный XML содержит клиентские данные с неизвестным правом публикации, сохраняем его локально и выясняем разрешение, не меняя утверждённый файл для маскировки.

## Изменение правил

1. Перед работой проверить `git status`, получить изменения remote и сопоставить ветки. Не затирать местные изменения; при расхождении согласовать содержимое.
2. Внести изменение в соответствующий документ и запись в CHANGELOG.md: дата, что изменилось и основание. Исправить зависимые инструкции, шаблоны и навыки в `skills/`.
3. Проверить ссылки, применимые тесты и согласованность. Изменение расчётной логики проверить отдельным исполнителем.
4. Создать осмысленный коммит; опубликовать через GitHub-коннектор или обычный git в этот же репозиторий. Пользователь уже поручил фиксировать здесь последующие изменения дисциплин; повторное общее разрешение не требуется.
5. Проверить удалённый commit SHA и совпадение дерева с локальными файлами. Если запись не прошла, прямо отметить «локально, GitHub не синхронизирован». Не применять force push.

Установленные навыки `~/.codex/skills/` — рабочие копии файлов из `skills/`. Изменения навыка сначала фиксируются в репозитории, затем переносятся в соответствующую установленную папку с проверкой различий. Память Groot содержит путь и принятые решения, но не конкурирующую версию дисциплин.

## Утверждённые XML

Путь: `products/<код-проекта>/<версия>/`. Версия, например `v001`, никогда не перезаписывается. Здесь хранятся точные байты XML или XML-содержимого GGE, решение об утверждении, проверочный протокол, отчёт проверки формата и manifest.json с SHA-256. Файл XML программы, XML экспертизы и GGE различать по назначению и схеме, а не только расширению.

Порядок: расчёт → отдельная проверка → исправление → решение начальника по точному хешу → локальный архив → коммит и публикация → проверка удалённой копии. Если задание требует утверждения заказчиком, в пакет включается фактическое свидетельство; внутреннее решение не выдаётся за подпись заказчика.

`tools/archive_xml.py` проверяет целостность входного пакета, синтаксис XML и записывает неизменяемую версию локально. Он не проводит XSD-экспертизу и не утверждает расчёт. Отчёт XSD либо основание его неприменимости готовится до архивирования; соответствие проверяет начальник.

```bash
python3 tools/archive_xml.py PROJECT-001 v001 /путь/к/approval.json
```

Формат approval.json — в templates/xml-approval.json. Пути входных файлов в нём относительны к файлу решения. Не заполнять PASS без фактической проверки.

После локального архивирования продукт имеет состояние «ожидает GitHub». После публикации сохранить commit SHA в локальном журнале `.local/publications/` либо в журнале проекта. Получить файл из этого коммита и проверить SHA-256 против manifest.json. Только после этого сообщать «сохранено локально и в GitHub». Сбой сети не отменяет локальное утверждение и не означает успешную синхронизацию.

История исправления: новая версия с причиной и ссылкой на прежнюю; прежний пакет сохраняется. XML не переформатировать после утверждения. `.gitattributes` сохраняет байты XML/GGE без изменения концов строк Git.

Фоновая синхронизация не запущена: публикация и проверка входят в завершение каждого поручения. Начальный репозиторий не содержит утверждённых производственных XML, поскольку таких документов ещё нет.

### Приложения к решению

В `attachments` задаются объекты с полями `file` (путь относительно решения), `sha256` и `purpose`. При `customer_approval_required: true` необходимо приложение с `purpose: customer_approval`. Файлы и хеши включаются в архив, но подлинность подписей оценивается проверяющим, не скриптом. Исходное approval.json сохраняется без изменения путей; фактические имена архивных копий перечислены в manifest.json. Неизменяемость версий обеспечивается процедурой и отказом скрипта от перезаписи; прямые правки обнаруживаются сверкой manifest и Git.
