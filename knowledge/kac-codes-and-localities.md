# КАЦ: группы КСР и населённые пункты

09.09.2026. Обязательная внутренняя проверка по поручению Алексея; не утверждение, что любая XSD требует непустого поля.

## Группа КСР

Для каждого оцениваемого ресурса подбирать группу по действующему официальному КСР, назначению и составу изделия. Проверять все вложенные предложения XML. В реестре сохранять код, название группы, редакцию и источник каталога, строку первоисточника и обоснование соответствия ресурса. Проверять также унаследованные коды.

Различать группу КСР, полный код ресурса, ОКПД2 и код субъекта РФ. Непустое поле не подтверждает корректность классификации. Не назначать одну группу всем материалам из одного КП или всем металлическим изделиям. Недостающие размеры не считать препятствием для выбора группы, если каталог на этом уровне их не разделяет.

Проверять книгу, часть и раздел, а не только название группы. Не сужать область группы до материалов нескольких её представителей. Готовность группы и техническую сопоставимость цены фиксировать отдельно. Методика и технические развилки — [исследование перед выбором КСР](ksr-technical-research.md).

При неоднозначности подготовить кандидатов с названиями, источниками и недостающим признаком; получить решение по office/workflow.md, раздел 1.1 до зависимого изменения XML. Не заменять неизвестную группу произвольным нулём. Специальный код для отсутствующего в КСР ресурса применять только после проверки правил программы, основания отсутствия и применимого решения пользователя.

## Населённый пункт и код субъекта

Сверять адрес каждого поставщика по его КП; разрешённое дополнение из Excel связывать с ячейкой. Адрес поставщика, склад отгрузки, адрес объекта и место доставки — разные сведения. Не выдавать юридический адрес за подтверждённый склад. Код региона объекта не распространять на всех поставщиков. При отсутствии нужного адреса подготовить конкретный вариант уточнения.

В XML ГРАНД-Сметы отдельно проверить реквизиты Counterparty и поля каждого Item: связь с поставщиком, StorageAddress и AdmRegionCode. Группу проверять в KSRGroup. Точные поля и допустимые значения сверять с целевой версией схемы, не переносить автоматически в другой формат XML/GGE.

По справке разработчика основная позиция КАЦ автоматически получает данные вложенного предложения с минимальной рассчитанной сметной ценой. Поэтому одинаковый населённый пункт в основных строках может объясняться выбором одного поставщика. Проверка обязана подтвердить это расчётом и правильной привязкой всех предложений; одного такого объяснения недостаточно, чтобы отклонить замечание пользователя. Проверку XML и наблюдаемое отображение в программе фиксировать отдельно. Не менять город выбранного предложения на город другого поставщика для разнообразия строк.

- [Позиции на основании коммерческих предложений — справка ГРАНД-Сметы](https://help.grandsmeta.ru/kon-yunkturnyj-analiz/sostavlenie-kon-yunkturnogo-analiza/kak-dobavlyat-pozitsii-v-kon-yunkturnyj-analiz).
- [Описание форматов ГРАНД-Сметы](https://xsd.grandsmeta.ru/).

## Обратная связь специалиста

При приеме ручной доработки применять [порядок разбора КСР](ksr-specialist-feedback.md): устойчивые идентификаторы и двойная нумерация, состав вложенных предложений, существование именно группы, полная иерархия, одинаковые ресурсы по всему документу и зависимые поля. Мнение автора и предполагаемую причину выбора не выдавать за техническое доказательство.

## КПП и полнота переноса — 15.09.2026

По прямому поручению пользователя недостающий в КП КПП разрешено искать в интернете по ИНН и дополнять в КАЦ. Сначала повторно проверить первичный документ, включая шапку, подвал, изображение и лист реквизитов: отсутствие в извлечённом JSON не означает отсутствия в КП. Затем использовать сведения ФНС и официальные реквизиты организации; вторичный справочник обозначать как вторичный источник.

Сохранять ИНН, КПП, источник, дату проверки и роль регистрации. Один ИНН может иметь разные КПП головной организации и подразделений. КПП филиала в конкретном КП не заменять головным автоматически. Изменение регистрационных данных после даты КП не переносить в исторический документ без проверки периода. При противоречии сохранить оба значения и основание принятого решения.

Проверять каждый Counterparty и все ссылающиеся Item. Дубли карточек с одним ИНН не гарантируют одинаковый адрес подразделения и КПП. Ведущие нули хранить строкой. Исправление считается перенесённым только после чтения итогового XML и разрешения ссылок Supplier; запись в журнале сама по себе не подтверждает перенос.

## Населённый пункт склада в каждой строке — 15.09.2026

По поручению пользователя графа населённого пункта склада проверяется у каждого вложенного предложения, а не только у выбранной основной строки. Искать сведения в КП и официальных источниках; известная сеть складов поставщика не доказывает точку отгрузки данного предложения. При отсутствии привязки подготовить конкретное допущение или запрос, согласовать способ заполнения. Разрешение искать КПП в интернете не является разрешением подменить склад юридическим адресом.

Подтверждённый склад и город поставщика, принятый отдельным решением как временное допущение, имеют разные статусы. Не менять регион организации на регион объекта ради заполнения склада. Поле StorageAddress, адрес Counterparty и AdmRegionCode использовать по семантике целевой схемы.


## Укрупнённое кодирование — поручение 15.09.2026

При невозможности обосновать подробную группу пользователь разрешил укрупнение, например до раздела 62.1.02. Это три сегмента кода, не три цифры. По проверенному п.24 Методики421/пр отсутствующие сегменты дополняются нулями: для данного примера 62.1.02.00. Название уровня и исходный раздел сохраняются в журнале. Укрупнение применять после проверки назначения по полной иерархии; отсутствие подробных характеристик не оправдывает выдуманный родительский раздел. Если даже ветвь классификации не установлена, код остаётся открытым.

Код ОКПД2 не заменяет КСР. Полный каталожный идентификатор может содержать оба классификатора; выбирать нужно именно часть КСР. Наличие кода во входящей ручной редакции не освобождает от проверки. XSD допускает строку KSRGroup и не проверяет существование кода в каталоге — прохождение схемы не подтверждает семантику. Укрупнённый код не подтверждает комплектность или заменяемость предложений.
